## 3. 처분 모델 (검수·회계의 단일 정의)

- **✅ 사용(use)**: 그래프화돼 데이터셋 편입(직접변환 또는 V2V/objocr 복구).
- **🛠 보정필요(fix)**: 살릴 수 있으나 아직 안 됨(위상 보정·V2V 대기·변환 실패·OBJ/OCR만). **변환·보정 성공 시 → 사용으로 이동**(보정필요↓·사용↑).
- **🚫 제외(excl)**: 영구 폐기 — 비-FP·중복 사본 둘뿐.
- **불변식**: 출처별 `사용+보정필요+제외 = 받은 원본`. 검수 콤보·종합 패널이 같은 소스 → 항상 일치.
- **검수 콤보 = 「라벨 구성 × 처분」 완전 회계** (한눈에 데이터 구성). 카테고리 고정 프레임, 숫자만 이동. → **ADR-0005**.

| `v2v_img` (이미지 직접) | 132,641 | 81,999 | **61.8%** |
| **합계** | **376,935** | **117,812** | **31.3%** |

전체 31.3%는 평균이지 성능이 아니다 — **이미지를 읽은 구간은 61.8%, 안 읽은 구간은 1.1%**다.
(문 레코드 수 ≠ 고유 문 수. 층 평면도는 세대 여러 개를 포함한다.)

### "누가"는 개인이 아니라 주체 구분이다

보정 작업자 **개인 식별 정보는 수집하지 않았다**. 결손이 아니라 **의도된 비수집**이다 —
공개 데이터셋에 작업자 식별자를 싣는 것은 개인정보 관점에서 피해야 한다.

필요한 "누가"는 **외부 라벨 / 우리 기계 / 사람** 세 범주이며, 그건 위 표로 전부 구분된다.
사람 작업의 품질은 **개인 식별 없이** 중복 이중주석 1,955쌍 IAA로 증명한다(§8.9 역할 95.0%).

**작업 시기는 연 단위로 기록한다 — 보정 작업은 2026년에 수행했다**(종료 2026-11-08, §8 머리말).
데이터셋 기술에 필요한 입도는 이것이고, 레코드별 편집 시각은 수집하지 않았다.

| 질문 | 상태 |
|---|---|
| 외부 / 우리 기계 / 사람 구분 | ✅ 전수 측정 — 위 표 |
| 축척을 사람이 넣었는지 기계가 추정했는지 | ✅ `meta.scale_source` — measured 94.0% / door_est 1.3% / 태그없음 4.7% (표본 3,000) |
| 사람이 남긴 작업 메모 | ✅ `meta.notes` 6.3%(표본 3,000) · 예: "애매한 공간 → 기타로 라벨링" |
| 사람 직접 vs 전파 복사 | ✅ **`meta.propagated` 있음** — True 18,018(59.0%) / False 12,524(41.0%) · `correction_source`·`propagated_from` 동반 |
| 검출기 버전 | ⚠ 값에 미기록 — 코드·`runs/` 디렉토리로만 추적 |
| 보정 작업 시기 | ✅ **2026년**(연 단위) · 종료 2026-11-08 |
| 작업자 개인 식별 · 레코드별 편집 시각 | **수집하지 않음(의도)** — 개인정보 비수집, IAA로 대체 증명 |


### 논문이 쓴 집합(gated 10,430)은 출처 구성이 전수와 다르다

위 표의 "parsed 절반이 우리 검출"은 **전수 기준**이다. 논문 α/v5가 실제로 학습·평가한
`tokens_korean_gated`(train 9,397 + val 492 + test 541 = **10,430**)는 구성이 다르다:

| 집합 | 방: AI-Hub 라벨 | 방: 우리 검출 | 구조: AI-Hub 라벨 | 구조: 우리 검출 |
|---|--:|--:|--:|--:|
| parsed 전수 41,409 | 49.1% | 50.9% | 41.0% | 55.6% |
| APT 한정 39,117 | 47.6% | 52.4% | 39.4% | 57.1% |
| clean 13,325 | 82.8% | 17.3% | 41.2% | 53.2% |
| **★ gated 10,430 (논문)** | **83.0%** | **17.0%** | **44.6%** | **50.5%** |

**APT 한정은 거의 영향이 없다**(49.1% → 47.6%; 데이터의 94.5%가 이미 APT). 구성을 가르는 것은
퍼널의 **clean 단계**다. 결과적으로:

- 논문의 *"transformed the annotations"*는 **방에 대해 83.0% 참**이다 — 과장이 아니었다.
- 다만 **구조(벽·개구부)는 50.5%가 우리 세그멘테이션 산물**이다 → 1문장 보강 필요.

### 어느 단계가 걸러내나 — 기하 게이트가 아니라 clean(메타) 단계다

퍼널 재현(논문 §3.1.2 수치와 일치, `EXPERIMENTS.md §토큰화 과정 데이터`에도 기록):

> parsed 41,409 → APT **39,117** → clean **13,325**(34.1%) → 기하 게이트 **10,485**(78.7%)
> → 토큰화 **10,430**(직렬화 한계 55장 제외)

**기하 게이트는 78.7%를 통과시킨다 — 느슨하다.** 최대 탈락은 그 앞 clean 단계(34.1% 잔존)다.
이걸 방 출처별로 분해하면:

| 방 출처 | APT 모집단 | → clean | 통과율 | → gated | 통과율 |
|---|--:|--:|--:|--:|--:|
| `label` (AI-Hub 주석) | 18,634 | 11,028 | **59.2%** | 8,713 | 79.0% |
| `v2v_img` (이미지 검출) | 13,454 | 1,637 | **12.2%** | 1,280 | 78.2% |
| `v2v` | 7,029 | 660 | **9.4%** | 492 | 74.5% |

**기하 게이트는 출처 중립이다**(74.5 / 78.2 / 79.0% — 사실상 동일). **편향은 전부 clean 단계에
있다** — 방이 우리 검출인 도면은 라벨 도면보다 **5~6배 덜 통과한다**(59.2% vs 9~12%).

구조 출처로는 이런 편향이 없다(clean 단계: label 35.6% · `v2v` **55.6%** · `v2v_img` 13.1%).
**가르는 것은 방 폴리곤의 출처**다.

### 논문 §3.1.2 서술 판정

| 항목 | 판정 |
|---|---|
| 퍼널 숫자(41,409·39,117·13,325·10,485·10,430) | ✅ **전부 재현됨. 오류 없음** |
| split 8,344/1,043/1,043 | ✅ 이미 9,397/492/541로 적색 정정 완료(`EXPERIMENTS.md`) |
| *"source annotations are incomplete … several units mixed in one record"* | ✅ **맞다** — 최대 탈락이 실제로 clean(완전 단일세대 판정) 단계다 |
| *"room boundaries that do not close"* | ⚠ 2차 요인 — 기하 게이트는 78.7%만 걸러낸다 |
| *"all serialized plans were produced by the automated pipeline alone"* | ✅ **참이다** — 토큰셋은 `parsed/graphs`에서 빌드, `corrected/edits`(사람 보정) 미반영 |
| *"manual corrections were applied in 1,565 cases"* | ⚠ 같은 문단의 위 문장과 충돌하는 것처럼 읽힌다. 어느 집합의 숫자인지 **명시 필요** |

**보강할 것 2개:**
1. **구조 출처 1문장** — 벽·개구부의 50.5%는 원본 주석이 아니라 우리 이미지 세그멘테이션 산물.
2. **선택 편향 명시** — gated 10,430은 무작위 표본이 아니라 **방의 83.0%가 AI-Hub 라벨**인
   쪽으로 치우친 집합이다. 일반화 주장의 범위를 여기에 맞춘다.

### 규모 상한 — 레버는 기하가 아니라 '완전 단일세대 판정'이다

우리 검출 방 도면이 라벨 수준(59.2%)으로 clean을 통과하면 (13,454 + 7,029) × 59.2% ≈
**12,100장**이 clean에 들어온다(현재 2,297장). 기하 게이트 ~78%를 곱하면
gated **10,430 → 약 18,000**(1.7배).

⚠ **상한이며 미검증이다.** 병목이 기하가 아니라 **메타(완전 단일세대) 판정**이므로, 검출기
정확도만 올려서 열리는지는 모른다. SPA 라벨이 없는 도면에서 **방 집합을 완전하게** 만들어야
한다 — 선결 과제는 "왜 완전 판정이 안 되는가"의 사유 분해다.

**정정(2026-11-10)**: 이 절을 처음 쓸 때 "전파 표지 필드 없음"으로 적었는데 **틀렸다**.
`dedup_review.propagate()`가 `meta.propagated=True` · `meta.correction_source` ·
`meta.propagated_from`을 기록한다(전수: True 18,018 / False 12,524). 최상위 키만 검사하고
`meta` 하위를 보지 않아 놓쳤다. 중복 서명 기반 추론값(12,524)은 필드값과 **정확히 일치**했으므로
결론은 바뀌지 않지만, 추론할 필요가 없었다. ⚠ `correction_source`는 두 의미로 쓰인다 —
옛 표본 전파(2건)는 출처 plan_id, 새 전파는 문자열 `'propagated'`. **판별은 `meta.propagated`로.**

### 논문 서술 규칙 (위반 시 즉시 정정)

1. **"AI-Hub 41,409장"으로 쓰지 않는다.** 방 49.1% / 구조 41.0%만 외부 주석이다.
   ⚠ **비율은 집합마다 다르다** — gated 10,430은 방 83.0%가 라벨이다. 숫자를 쓸 때 **어느 집합인지
   반드시 명시**할 것(전수 / APT / clean / gated).
2. **우리가 만든 값은 그렇게 쓴다.** 스윙·복도 노드·기구 방배속은 우리 산물이다.
3. **상수는 상수라고 쓴다.** `size_mm`은 가정한 표준 치수이며 측정값이 아니다.
4. **검출값과 사람값을 한 칸에 넣지 않는다.** §8 본문이 전파본 18,018을 사람 보정에 합산해
   방 수 증감 결론이 뒤집힌 전례가 있다(+9.3% → −2.0%).

### ③층은 이 표에 "우리 기계" 행을 더하는 일이다 (§8.11 참조)

**층을 분리해 두면 디렉토리 자체가 출처 기록이다** — 값마다 출처 필드를 박을 필요는 없고,
출처 서술은 이 문서가 담당한다.

## §8.13 중복 통일 범위는 **split 방식에 의존한다** (2026-11-10 전수 측정)

> ⚠ **숫자 정정 [2026-11-13]** — 아래 수치는 **주석↔도면 오매칭 171장을 걸러내기 전**의 것이다.
> 정정된 값은 **§8.14**: gated 10,485→**10,383** · 고유 2,743→**2,736** · 보정 9,033→**8,971** ·
> test 417장/고유136→**403장/고유135** · 불일치 1,124→**1,116**. 결론(복도·split 의존성)은 그대로다.

측정 = `scripts/dedup_split_impact.py`(읽기 전용) · 작업표 = `data/staging/dedup_test_blockers.csv`

§8.8은 "남은 인간 작업 = A+C 135그룹"으로 닫혀 있었다. 그 숫자는 **지금의 split
(plan_id 해시)을 전제로 한 것**이고, split을 고치면 달라진다. 순서를 바꿔 재면:

| | 지금(plan_id 해시) | 그룹 서명 해시 |
|---|--:|--:|
| 불일치 그룹이 train/test를 **가로지름** | **56그룹** · test 94장 | **0** — 구조적으로 불가 |
| test에 떨어진 불일치 그룹 | 56 | **17** (A구조 12 · B라벨 4 · C위치 1) |
| 그중 대표 동결로 내용이 바뀌는 보정본 | — | **22장** |
| train 쪽 불일치 | — | 157그룹 · 바뀌는 보정본 **219장** = 보정 9,033의 **2.4%** |
| gated test | 546장 / 고유 300 (사본 1.8배) | **417장 / 고유 136** (사본 3.1배) |

§8.8의 **255장**과 모순이 아니다 — 255 = train 219 + val 14 + test 22. 같은 측정이고,
split을 고치면 그 255장이 **어디로 떨어지는지**가 보인다는 것이 §8.13의 내용이다.

**결론 2개.**

1. **train 쪽 불일치는 성능 문제가 아니다.** 바뀌는 219장은 보정본의 2.4%로,
   3-seed 표준편차(±1.4~2.0pp, EXPERIMENTS)보다 작다. → **통일하지 않고 불일치를 보존한다.**
   이게 §8.9 IAA 95.0%의 원자료다. 통일하면 측정의 근거가 사라진다.
2. **남는 문제는 평가 정답지의 모호성 하나**이고 그 범위는 135그룹이 아니라 **17그룹**이다.

### ⚠ 같이 드러난 것 — test 고유 136개 중 **49개는 보정이 아예 없다**

| 서명해시 test 고유 136개 | 그룹 상태 |
|---|--:|
| 보정 없음(`none`) | **49** |
| 단일 보정(`single`) | 57 |
| 사본끼리 일치(`agree`) | 13 |
| 사본끼리 불일치(`conflict`) | **17** |

**평가 정답지의 36%가 사람 보증이 없다.** §8.7이 미보정 10,867장을 "학습 효과 없음"으로
처분한 것은 **학습 쪽에선 맞지만 평가 쪽에선 틀렸다** — 평가셋에도 구멍이 있다.

→ 사람이 더 해야 할 일의 **전부** = 불일치 17그룹 대표 확정 + 보정 없음 49장 = **66건**.
외부 작업자를 다시 부를 크기가 아니다. 이걸 하면 평가셋이 **100% 사람 보증**이 된다.

### §8.7의 처분표 정정 — gated 구멍 1,452장은 전부 규칙 대상이 아니다

| gated 미보정 1,452 | 수 | 처리 |
|---|--:|---|
| **보정된 사본이 있다**(사람 직접 보정 형제) | **280** | **전파** — 사람 품질을 복사한다. 규칙이 아니다 |
| 사본이 없다 | **1,172** | 규칙 → `refined/`, `verified_by="rule"` |
| 그중 **test에 떨어진 것** | — | **규칙 금지 · 사람만** (기계 정답지로 기계를 채점하면 순환논리) |

서명해시 split에서는 그룹 전체가 한 split에 들어가므로 **전파가 split을 넘지 않는다** —
지금의 plan_id 해시에서는 전파가 곧 누수였다.

미보정의 나머지: 게이트밖 APT **7,220**(학습 코퍼스 영향 0 · 도면화 개발용) ·
ROW 1,546 + DEH 649 = **2,195**(규칙 금지 — 오염 0 일반화 평가셋, §8.7 ③).

### 규칙 결과는 `corrected/edits`를 덮지 않는다

규칙 적용은 '보정'이 아니라 **실험 조건**이다. 덮어쓰면 "역할 82.1% 사람 보증"(§8.2)이
희석되고 되돌릴 수 없다. 레이어 ③ `refined/`에 쓰면 **사람 / 규칙 / 미보정 3단 ablation**이
생긴다 — 레이어 분리가 출처 기록이라는 §8.12의 원칙 그대로다.

## §8.14 AI-Hub 원천의 주석↔도면 오매칭 — 발견·피해·조치 [2026-11-13]

  반대로 크기만 잡은 것 5시트(사본 없음).

## §8.16 연결층·개구부·벽두께는 **우리가 다시 만든다** — 받은 값과 만든 값의 경계 [2026-11-13]

사용자 결정: *"이미 AI-Hub가 제공하는 것도 있고 우리가 만든 것도 있을 텐데… 사실 무시하고
우리가 새로 만들어도 되는 것 아닌가. 그들이 주는 값은 이것만 활용하고 우리가 새롭게
만들었다, 이런 식이 나을 것 같다."* — 그대로 채택한다. 근거는 아래 실측이다.

### 8.16.1 AI-Hub 라벨에는 **관계 필드가 하나도 없다** (전수 확인)

라벨 zip 8개(TL_/VL_ × SPA·STR·OBJ·OCR)의 JSON은 **순수 COCO**다.

```
최상위       categories · images · annotations
annotation   id · image_id · category_id · segmentation · area · bbox · iscrowd · attributes
```

`conn*`·`rel*`·`room*`·`adj*`·`link*`·`from`·`to`·`pair` 류 키를 전수 검색 → **0건**.
카테고리는 23개(공간 12 · 구조 3 · 객체 5 · OCR · background)이고, `attributes` 에
담긴 실제 정보는 다음뿐이다(TL_SPA/STR/OBJ 각 300장 표본).

| attributes | 값 | 건수 |
|---|---|---|
| `occluded` | False | 전건 |
| `창호` | 미닫이창 / 기타창 / 여닫이창 | 624 / 155 / 17 |
| `구조_벽체` | 기타벽 / 철근콘크리트벽 | 1,297 / 837 |
| `구조_출입문` | 여닫이문 / 미닫이문 / 기타문 | 213 / 10 / 1 |
| `rotation` (OBJ) | 0.0 외 2건 | 4,501 |

### 8.16.2 경계표 — 받은 것 / 우리가 만든 것

| 층 | 받은 것(AI-Hub) | 우리가 만든 것 |
|---|---|---|
| 방 | 폴리곤 `segmentation` · 역할 `공간_*` | 역할 보정 · 복도 복원 · 파우더룸 분할 · **직선화** |
| 벽 | `구조_벽체` 폴리곤 · 철근콘크리트벽/기타벽 | 중심선 `segment` · `type`(exterior/interior/open) · **`thickness_mm`(상수)** · `rooms` · `openings` |
| 문 | `구조_출입문` 폴리곤 · 여닫이/미닫이/기타 | `connects` · `on_wall` · `width_px` · 스윙 `orientation` |
| 창 | `구조_창호` 폴리곤 · 미닫이창/여닫이창/기타창 | `belongs_to` · `width_px` · `orientation_deg` |
| 기구 | bbox · `rotation` | `size_mm`(상수) · 방 귀속 |
| 그래프 | **없음** | `edges` 전부 · `privacy_transition` · `dist_from_entrance` |
| 축척 | 없음(OCR 인쇄만) | 사람이 입력 97.6%([[alba-correction-closed-accounting]]) |

→ 논문 서술은 *"AI-Hub에서 받은 것은 폴리곤·역할·개구부 상자·종류·기구·OCR 이고,
그래프(연결)·치수·두께는 우리가 만들었다"* 가 **사실 그대로**다.
`구조_벽체` 의 철근콘크리트벽/기타벽 구분은 **현재 버리고 있다** — 복구 대상.

### 8.16.3 연결층이 왜 엉터리인가 — 한 뿌리에서 나온 낡은 값

`walls[].rooms` → `doors[].connects` → `edges` 는 **파싱 때 한 번, 보정 전 폴리곤으로**
계산되고 그 뒤 갱신되지 않는다. 에디터는 이 필드를 화면에 띄우지 않으므로
**사람이 검수해도 잡히지 않았다.** 방-방 직결을 고치려고 만든 프로그램인데
정작 그 원인을 손댈 수 없었던 셈이다.

실측 `APT_FP_396cb308_17447720_u3`:
- 문 d0 이 올라탄 벽 **w14 는 길이 21px 조각**인데 `rooms:[70,72]`(침실+침실)이고,
  `connects` 가 그걸 그대로 베꼈다 → **침실↔침실 문**.
- 같은 문 상자가 **벽 조각마다 한 레코드**씩 생겼다(d1=w19 · d2=w20 / d7=w43 · d9=w40).
- `bbox_px` 가 **없는 빈 문 레코드**(d5)가 섞여 있다.

### 8.16.4 축선을 벽으로 검출한다 — 개방이 사라지는 원인

300px 넘는 벽 레코드는 **도면을 가로지르는 제도 축선**이다. w81 은 y=784.2 위의 길이
569.7px `exterior` 200mm 레코드인데 그 선은 주방 아랫변·알파룸 아랫변·거실 윗변·복도
윗변을 한꺼번에 지난다(해당 도면의 300px 초과 벽 4개 모두 같은 성격).
메모리의 *"얇은 회색선은 축선이지 벽이 아니다"* 가 수치로 확인된 것이다.

→ 이 축선 하나가 주방↔거실 경계 229px 를 "벽으로 덮었다"고 판정해 개방 엣지를 지웠다.
**고침**: 막힌 구간 = (두께 있는 벽) − (개방 기록). 축선은 개방 구간을 가리지 못한다.

**원천에는 있다.** TL_STR 400장의 `구조_벽체` 폴리곤 중 길쭉한 조각 1,898개의 짧은 쪽은
13~19px 에 뚜렷한 최빈(15~16px)을 만든다. 파이프라인이 이걸 **중심선 + 상수**로 줄였다.

판정 — **등급은 필요하고 벽별 측정값은 불필요하다.**
- 필요: 벽이 두께를 가진다는 사실과 **두 등급(내벽/외벽)의 대표값**. 도면화에 벽 두께 없이
  벽을 그릴 수 없고, 코덱의 코너 공유 가정이 깨지는 지점이 정확히 이 필드다
  ([[korean-codec-rplan-optimized-wallthickness]]).
- 불필요: 벽 하나하나의 측정 두께. 복구해도 측정 오차(±1px ≈ ±17mm)가 실제 변동보다 크다.
- 할 일: 상수를 유지하되 **원천 벽체 폴리곤에서 측정한 대표값으로 교체**하고,
  버리고 있는 `철근콘크리트벽/기타벽` 구분을 받아온다.

### 8.16.8 적용 순서 (의존이 있다)

1. **직선화** `snap_axis`(tol 4→6, 수렴까지 반복) + `deburr`(되돌아오는 떨림만)
   — 뒤 단계가 전부 폴리곤에 의존한다.
2. **연결층 재산출** `rebuild_links` — 직선화한 폴리곤이 있어야 맞닿음 판정이 선다.
3. **개구부 치수** `fix_openings` — 1·2와 독립이지만 벽 방향을 쓰므로 벽 정리 뒤가 낫다.
4. **문 위치 보정** `snap_doors` — 2 가 배선을 정하고 1 이 벽을 세운 뒤라야
   맞닿은 띠가 나온다(§8.16.9).
5. **파우더룸·복도 보완** — 방 개수를 바꾸므로 기하가 정리된 뒤에.
6. **벽 두께 복구** — 원천 재파싱이 필요해 가장 뒤.

7. **전파 재생** `reprop_all` — ⚠ **빼먹으면 사용자 확정값이 사본에서 사라진다.**
   `link_overrides.json` 은 **plan_id 로** 걸린다. 전수 재산출을 돌리면 원본만 확정값을
   받고, 같은 그림의 사본은 기하에서 다시 뽑은 값으로 돌아간다. 실측(2026-11-14):
   전수 적용 직후 전파본 **62장이 전부** 갈렸다(c6f3a6f8 u1 문 11·외부문 1 ↔
   사본 문 7·외부문 0). `reprop_all --apply` 로 재생하면 62장 전부 복구되고
   `verify_prop` 어긋남 0 이 된다. 근본 해법은 override 를 **그림 단위**로 거는
   것이지만 전파 변환(평행이동·미러)을 좌표에 다시 먹여야 해서 미뤘다.

기록: 모든 적용은 `_edit_log.jsonl`(§8.15)에 `actor=claude` · `kind=correct` 로 남긴다.
`rebuild_links` 는 `provenance.links="geometry_rebuild"`,
`fix_openings` 는 각 개구부에 `size_source="geometry_rebuild"` 를 박는다.


### 8.16.9 문 위치가 **84.6% 벽 밖에 있었다** — 원인은 스윙 호 상자 [2026-11-13 전수]

사용자가 도면마다 같은 지적을 반복했다: *"나머지는 문의 위치만 조정해줘."*
원인은 하나였다. **AI-Hub 문 주석의 `bbox_px` 는 여닫이 호(swing arc)를 감싼
상자**다. 그 중심은 경첩도 벽도 아니라 호의 한가운데라서, 문 위치가 늘 방
안쪽으로 밀려 앉는다.

규칙 (`scripts/snap_doors.py`): 문이 잇는 두 방의 **맞닿은 띠**(서로의 버퍼가
겹치는 영역 = 벽) 위에서 현재 위치와 가장 가까운 점으로 옮긴다. 방 폴리곤은
직사각화(§8.16 계열)를 거쳐 믿을 만하다. `position_source` 가
`user_override` / `tag_detect` 인 문은 건드리지 않는다. 옮길 거리가 60px 을
넘으면 배선 자체가 의심스러우니 그대로 두고 센다.

전수 결과 (30,533장 · 보호 10장 제외 · 실패 0건 · 9.2분)

| 항목 | 값 |
|---|---|
| 벽 위로 옮긴 문 | **187,513** (문 221,590 중 **84.6%**) |
| 바뀐 도면 | 28,671 / 30,533 (93.9%) |
| 60px 초과라 보류 | 4,102 |
| 사람·태그 확정이라 건너뜀 | 5 |

벽에서 떨어져 있던 거리 (표본 4,000장 · 24,463개 문)

| 지표 | px | mm |
|---|---|---|
| 중앙 | 23.0 | **333** |
| p25 / p75 | 16.7 / 28.4 | — / 396 |
| p90 | 35.5 | 456 |

구간 분포: 0~10px 11.0% · 10~20px 25.8% · **20~30px 43.3%** · 30~40px 13.7% ·
40~50px 4.3% · 50~60px 1.8%.

**원인 확증** — 이 거리는 벽 두께 같은 상수가 아니라 **문 폭에 비례한다**.
표본 17,922개 문에서 `이동거리 / 문폭` 의 중앙값은 **0.339**(p25 0.253 ·
p75 0.393). 상수였다면 비율이 문 폭에 따라 흩어졌을 것이다. 호를 감싼 상자의
중심이 벽에서 문 폭에 비례해 떨어진다는 설명과 맞는다. (0.5 가 아닌 것은
미닫이문의 상자가 호가 아니라 얇기 때문이고, `width_m` 이 §8.16.6 에서
**벽 방향 길이**로 재산출된 값이기 때문이다.)

의미: 이 교정 전에는 "문이 어느 벽에 붙어 있는가"를 좌표로 물을 수 없었다.
생성 모델의 개구부 토큰(`openings[].pos`, 변 위 16분할)은 문이 **변 위에**
있다는 전제에서만 뜻이 있으므로, 이 교정은 코덱의 전제를 비로소 참으로 만든다.

보류한 4,102개(60px 초과)는 위치가 아니라 **배선**이 의심스러운 쪽이다 —
따로 봐야 한다.
