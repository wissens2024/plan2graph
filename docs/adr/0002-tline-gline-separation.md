# ADR-0002: T-라인 / G-라인 분리 — 두 생성 패러다임을 폴더·GUI에서 격리하고 도면 품질로 합쳐 비교

Status: Accepted (기하 부분 방향정정 2026-06-11)
Date: 2026-06-09
Deciders: wissens2024

> **⚠️ 방향 정정(2026-06-11):** **treemap은 폐기 예정 임시 스파이크**다 — 사업계획서엔 없고(계획 목표 = "온톨로지 기반 **공간배치 생성 AI**"), 빨리 도면을 보여주려 급조한 규칙기반 placeholder였다. **기하 좌표는 T·G 둘 다 생성형 AI(`geom_gen`, 학습모델 `geom_g0` 작동)가 생성**하는 게 목표다. 아래 "T-라인 = 규칙기반 treemap이 정체성"은 임시 구현 기준 서술이며, **T 버튼을 AI로 옮긴 뒤 treemap 코드는 제거**한다(단 `floorgeom.share_wall`은 공용 verify(인접 실현)용이라 유지). 라인 분리(폴더·GUI)·"도면품질로만 비교" 원칙은 유효. [[treemap-deprecated-generative-is-goal]]

## Context
도면 생성에 **두 가지 방식**이 생겼다. 둘은 데이터셋·스키마·SVG·생성 방식이 **전부 다른 별개 패러다임**이다.

- **T-라인(기존)**: AI-Hub 검출(SPA+STR) → **자동 변환** → 그래프(`topology.py`/`schema.py`, `releases/v0~`). SVG 없음. 위상 풍부(엣지 via=door/open/balcony, `door_type`, `n_doors`, `validation` R1~R5), 기하 빈약(centroid만). 좌표 도면 = **규칙기반 treemap(`floorgeom.py`)** — 학습 모델 아님.
- **G-라인(신규 설계)**: 사람이 `topoedit`에서 **SVG(좌표·모양 = 단일 진실)** 편집 → 추출 → geometry-rich 그래프(위상+기하, `releases/g0~`). 좌표 도면 = **학습된 기하 모델(`train_geom.py`)**.

그런데 신규 g0가 설계(SVG 사람 교정)를 건너뛰고 `init_state`+`geomgraph` **지름길로 자동 생성**돼 위상이 간소화됐고(엣지 0.18/방, `door_type`·`area_m2`·`fixtures` 결손, 역할 34% 기타), 두 스키마(`layout.nodes` vs `rooms`)가 한 폴더·한 메뉴에 **섞여** 혼란을 일으켰다. 분석 과정에서 "상위개념으로 합치자"는 제안이 나왔으나, 방식이 다른 둘을 섞으려 한 오판이었다.

## Decision
T-라인과 G-라인을 **완전히 분리**한다 — 절대 한 스키마로 합치지 않는다.

1. **폴더 분리**: `data/releases/{tline,gline}/`, `runs/{tline,gline}/`.
2. **GUI 분리**: 라인별 섹션(데이터셋 · 위상모델 · 도면생성)을 따로 둔다. 단 **성능 비교는 한 화면에 합쳐서** 본다(최종 잣대 = 도면 품질).
3. **기하 생성 방식이 라인의 본질 차이다**:
   - T-라인 = **규칙기반 treemap(모델 없음)** → 개선 = treemap 알고리즘(코드).
   - G-라인 = **학습 기하 모델(`train_geom`)** → 개선 = 데이터·학습.
4. **위상 모델**: T-라인은 조합 자유(combine/따로, 많은 조합), G-라인은 **조합 적게** 하고 **기하·도면생성에 집중**.
5. **지금은 자동화만으로 구조·품질을 올린다.** 사람(알바) 검수·편집을 통한 데이터셋 업그레이드는 이후 단계.
6. **작업 순서**: ① 폴더·GUI 구조화(분리) → ② G-라인 스키마 정교화(자동).

### 두 라인 끝-에서-끝 정의
| | T-라인 | G-라인 |
|---|---|---|
| 데이터셋 | v0~ (위상, 자동 detection→그래프) | g0~ (위상+기하, SVG/추출) |
| 원천 방식 | 검출→자동 변환 (SVG 없음) | 사람 SVG 편집→추출 (SVG=단일 진실) |
| 스키마 | `layout.nodes` (type/source-target) | `rooms` (role/from-to/polygon) |
| 위상모델 | combine·따로 자유(많이) | 조합 적게 |
| 기하 생성 | 규칙기반 treemap (모델 없음) | 학습 기하모델(train_geom) |
| 개선 레버 | treemap 코드 | 데이터·학습 |
| 최종 비교 | → **도면 품질** ← | → **도면 품질** ← |

## Considered Alternatives
1. **상위개념 스키마로 통합**(T·G를 한 superset로) — **기각**: 방식 자체(자동 detection vs 사람 SVG)가 달라 한 스키마로 묶으면 의미가 깨진다. 결정자 명시 "절대 섞지 말 것".
2. **한 메뉴에 위아래 스택**(현행 도면생성) — **기각**: 한 스크롤에 두 관습이 섞여 혼돈. 숫자(세대수)만 보이고 내용 차이가 숨겨졌다.
3. **폴더는 그대로 두고 prefix(v*/g*)로만 구분** — **기각**: 폴더·GUI에서 명시적 분리를 요구(섞임 원천 차단).
4. **T-라인에도 학습 기하 모델 추가** — **기각**: T-라인 기하는 treemap이 정체성. 모델을 G-라인 전용으로 두어야 *규칙기반 vs 학습* 대조 실험이 성립.

## Consequences
- Positive: 두 패러다임이 독립 진화(데이터셋 검수·학습·알고리즘을 라인별로). 도면 품질로 **공정 비교**(규칙기반 vs 학습). 스키마 혼선·은폐 제거.
- Negative: 폴더 이전으로 `releases/<v>` 경로 참조 다수 수정 필요(1회). GUI 메뉴 재편 비용.
- Follow-up: ① 폴더 마이그레이션 + 경로 상수화(무손실, GUI health 확인) → ② GUI 라인 분리 + 합친 비교 뷰 → ③ G-라인 스키마 정교화(문서 갱신 후) → ④ [DATA.md](../DATA.md) §4 레이아웃을 라인 하위폴더로 갱신(완료).

## Assumptions
- 두 라인이 계속 병존하며 각자 발전한다(한쪽 폐기 전제면 분리는 과설계).
- 최종 평가는 **도면 품질** 단일 기준(둘을 합쳐 비교 가능).
- 지금 단계는 자동화로 충분(사람 검수 없이도 구조·품질 향상 가능).
